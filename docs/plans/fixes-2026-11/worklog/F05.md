## Plan correction (stale / inaccurate)

- The plan's concern that `getRgbPenColor` makes the overview pastel is not
  supported by the code. `src/qml/qmlwaveformoverview.cpp:431-450` computes
  `red/green/blue` from the per-band values and then divides all three by
  **the maximum component** (not the sum, not 255). The deck's shader renderer
  does the identical normalisation at
  `src/waveform/renderers/allshader/waveformrendererrgb.cpp:210-222`. Dividing
  by the largest channel can only raise the other channels toward the maximum;
  it cannot desaturate. So no C++ change was made: with these tokens a
  single-band column reaches exactly the token colour, and a full-range column
  normalises to near-white.
- The plan's line references to the old literals are still valid (the files
  are unchanged on `main`), only the defaults moved.

## Token values and blend check

The three values are the ones the plan suggested and survived a numeric check,
so no tuning was needed. Both renderers compute
`c = low*lowToken + mid*midToken + high*highToken` and then divide by
`max(r,g,b)`:

| Band content (low/mid/high) | Result   | Reading                     |
| --------------------------- | -------- | --------------------------- |
| 1 / 0 / 0                   | `#FF3B30`| pure bass, token-exact      |
| 0 / 1 / 0                   | `#40FF6C`| pure mids, green            |
| 0 / 0 / 1                   | `#3D87FF`| pure highs, blue            |
| equal mix                   | `#EBFFF5`| trends white, not grey      |
| 200 / 60 / 30 (kick)        | `#FF8166`| red / orange                |
| 40 / 180 / 60 (vocal)       | `#7CFFAE`| green                       |
| 20 / 40 / 160 (hats)        | `#61B0FF`| blue                        |
| 150 / 140 / 130 (full mix)  | `#F7FFEF`| near white                  |
| 150 / 10 / 120 (bass+hats)  | `#FF94D1`| magenta crossover, expected |

The numbers are the documented blend, not a screenshot; see the caveats below.

## Behaviour notes for the reviewer

- The overview component takes a single `colorLow/Mid/High` set for every
  overview renderer. A user on `waveformOverviewType` 0 (Filtered) or 1 (HSV)
  therefore also sees the new band hues, in the same positions and order as
  before; only the default colours changed. Leaving those renderers on the old
  purple would have meant a second, unowned colour set in the same component.
- `res/qml/Sampler.qml:151` reuses `Skin.WaveformOverview`, so sampler overviews
  get the same new default colours. That is consistent with the deck and not a
  renderer regression.
- The user's waveform type choice is untouched: switching to Filtered, HSV or
  Simple still shows exactly what it showed before, because those blocks were
  not edited.
