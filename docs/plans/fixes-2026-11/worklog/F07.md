## Linux x64 / Test investigation (2026-11-20)

The PR's only red job is `Linux x64` / `Test`; the annotation is just
`Process completed with exit code 8`, and the Actions log endpoint requires
admin rights, so the exact failing assertion could not be read. What the run
does show is a timing clue: on `main` the `Test` step took **105 s**
(run 44622329416), on this branch **219 s** (+114 s). The bounds test has eight
`checkSize` calls (five sizes plus the three preview/4-deck passes). If the
settle check fails at each one it spends the full 8 s window plus the 1 s
sample loop, i.e. roughly `8 x 9 = 72 s`, on top of the 15 s creation wait and
the 3 s preview waits. That is the size of the regression, which points at the
**layout never settling**, not at a single straight bounds number.

Arithmetic for the band, from the QML tokens (`space1` = 4, `space4` = 16,
`space5` = 24 at `uiScale` 1):

- pane: `112 (deckPaneHeight) - 16 (tab row) - 4 (gap) = 92`
  (`Theme.deckPaneContentHeight`), which is what the test measures.
- loop card: `2 (border) + 2 x 2 (inset) + 16 (header) + 39 (beat) +
  24 (action) + 24 (roll) + 3 x 1 (gaps) = 112`.
  The beat row is `112 - 2 - 4 - 16 - 24 - 24 - 3 = 39`.
- loop content: `16 + 39 + 24 + 24 + 3 = 106`, inside `112 - 2 x 3 (margins)
  = 106`. It fits exactly, at 0.75 and 1.25 `uiScale` too.

### Defects found and fixed

1. **Tab row was the one item with contradictory size hints.** A `Skin.Button`
   implies 26 px, while Deck.qml capped the `DeckPaneTabs` row at 16 px. Only
   the attached maximum/minimum/preferred were set; the row's own implicit
   preferred height stayed 26. That is the one unresolved conflict in an
   otherwise exact-fit band, and a layout that has to reconcile a 26 px child
   hint with a 112 px parent can shrink the row and the pane by a few pixels to
   make the sum fit. The tab delegates now pin `implicitHeight`,
   `Layout.preferredHeight` and `Layout.maximumHeight` to
   `Theme.deckPaneTabHeight`, so the row advertises exactly 16 at every level.
   The pane host also no longer sets an explicit `height` while it is a
   `GridLayout` child; min/max/preferred own that geometry.
2. **Negative sizes before the first layout pass.** `beatKeysRow.height` was
   `parent.height - 6`; the parent is 0 until the layout runs, so the binding
   was -6 and the beat-key font (`height - 8`) was -14/-8. Linux's font engine
   resolves an invalid pixel size differently from macOS; the row is now
   `Math.max(0, ...)` and the font is floored at 1 px.
3. **Loop card and pane host had no maximum height.** Both were pinned only by
   minimum + preferred, so a taller row could stretch one of them away from the
   other. Both now use the band height for min/max/preferred.
4. **Scrollbar thumb could exceed its track** at a very narrow card
   (`Math.max(12, ...)`); it is clamped to the track.
5. **Docs widths were wrong**: they claimed 276 px at 1440 and 452 px at 1792;
   the measured panes are 273 and 309 (the 135 px FX-assign column appears from
   a 708 px deck). Corrected, with 693 px at 2560.

### Assertion change

The pane floor `90` and the tab floor `16` are now read from
`Theme.deckPaneContentHeight` and `Theme.deckPaneTabHeight`, and both tokens
are pinned with `EXPECT_EQ(92, ...)` / `EXPECT_EQ(16, ...)` in the same test.
`90` was an arbitrary 2 px of slack below the approved design; testing the
token makes the assertion stricter and stops a future Theme edit from silently
lowering the bar. No assertion was weakened.
