```cpp
// src/track/beats.h:60
struct DownbeatInfo {
    bool valid = false;
    int beatsPerBar = 4;
    int phase = 0;          // zero-based index of the first downbeat
    float confidence = 0.0f;

};

// src/track/beats.h:331

```

- Parsed once in the `Beats` constructor from the sub-version string
  (`beats.h:193`, `beats.cpp:29-66`). Fragments are `|`-separated
  `key=value`: `db`, `dbbar`, `dbphase`, `dbconf`, `dbsrc`.
  `parseDownbeatInfo` only sets `valid` when `db=1` **and**
  `0 < dbbar` **and** `0 <= phase < dbbar`; otherwise the struct stays at its
  defaults (`valid=false`, `beatsPerBar=4`, `phase=0`), which the renderer
  treats as "no metadata". There is no separate "bar unknown" flag beyond
  `valid`.
- The writer (`src/analyzer/analyzerbeats.cpp:317-322`) stores
  `|db=1|dbbar=..|dbphase=..|dbconf=..|dbsrc=..` on the same sub-version the
  beat grid already carries, and the reader strips those fragments before it
  compares sub-versions (`analyzerbeats.cpp:31-32`), so older builds ignore
  them.
- The producer (`src/analyzer/plugins/analyzerparamixbeats.cpp:102-114`)
  reports `valid=true`, `beatsPerBar = m_result.beatsPerBar` (falling back to
  4), `phase = m_result.downbeatPhase`, `source = pluginInfo().id()`.
  The analysis engine documents `beatsPerBar` as "always 4 for the currently
  supported material" and `downbeatPhase` as "the anchor is the downbeat, so
  this is 0 for a freshly analyzed grid"
  (`lib/paramix-analysis/include/paramix/analysis/analysis.h:26-33`).
  So in practice `phase` is 0 today, but the renderer honours any value the
  schema allows.

### True semantics of `phase`

- It is a **beat ordinal, not a time offset**: the index of the first downbeat
  counted from the grid origin, i.e. the grid's first beat. It is *not* frames
  and *not* seconds, so tempo changes do not alter it. A beat is a downbeat
  when `(beatIndex - phase) mod beatsPerBar == 0`.
- The grid origin is the first beat the iterator counts from:
  `m_lastMarkerPosition` for a constant grid (`cfirstmarker()` has beat offset
  0), and the first `BeatMarker` for a beat map. `iteratorFrom()` resolves
  every position against that same origin
  (`src/track/beats.cpp:467-518`), so beat ordinals are consistent across tempo
  changes: the iterator adds integer beat offsets and per-marker beat counts,
  never a fractional time division.
- Grid edits:
  - `tryTranslate()` / `tryTranslateBeats()` (`beats.cpp:663-694`) move every
    marker and the origin by the same delta, and keep `m_subVersion`; the
    ordinal of a given musical beat relative to the origin is unchanged, so the
    bar pattern stays aligned with the audio.
  - `tryScale()` (`beats.cpp:696-750`) keeps origin and sub-version, scales the
    BPM. Beat ordinals stay valid, so bars still start on `phase`; the bar
    *duration* in seconds follows the new tempo. For the 2:1 cases (`Halve`,
    `Double`) this doubles/halves the bar duration, which is the follow-up
    risk recorded below.
  - `trySetBpm()` (`beats.cpp:752-755`) rebuilds a constant grid anchored on
    the old first marker and keeps `m_subVersion`; origin unchanged, ordinal
    semantics unchanged.
  - No edit path rewrites `phase` or `beatsPerBar`. That is consistent with
    `phase` being relative to the grid origin, except for the 2:1 tempo edits.

## Step 2 - stable beat index

The iterator starts at the first **visible** beat, so a loop counter would
restart with the viewport. The index is derived from the grid instead:

```cpp
auto it = trackBeats->iteratorFrom(startPosition);
int beatIndex = (it == trackBeats->cend())
        ? 0
        : static_cast<int>(it - trackBeats->cfirstmarker());
for (; it != cend && *it <= endPosition; ++it, ++beatIndex) { ... }
```

`ConstIterator` is a random-access iterator (`beats.h:95-181`) with the
origin at `cfirstmarker()`:

- **Constant grid**: all beats share one marker and differ only in
  `m_beatOffset`, so `it - cfirstmarker()` is *exactly* the integer beat
  offset. That offset was itself derived from the anchor and beat length by
  `iteratorFrom()` (`ceil((position - anchor) / beatLength)` for positions
  after the anchor, floor-based division for positions before it). No extra
  rounding is needed, and no fractional division can drift: the ordinal is an
  integer, computed by the grid's own iterator.
- **Beat map**: `operator-` sums each marker's `beatsTillNextMarker` between
  the two iterators, i.e. the marker/beat count (`beats.cpp:173-192`). One
  call per frame for the first visible beat, then `++beatIndex` per beat.
- **First beat before frame 0**: the renderer clamps the viewport to frame 0
  (`startPosition = max(firstDisplayed, kStartFramePos)`), but `iteratorFrom`
  still counts from the grid's first beat, so the first visible beat keeps its
  true ordinal (e.g. beat 2 for a grid whose beat 0 is at -2 beats). Those
  pre-zero beats produce a negative ordinal when the viewport starts before
  the grid origin, and `isDownbeat()` handles negatives with a double modulo.
  The test `GridStartingBeforeFrameZeroKeepsTheGridOrigin` pins this down.
- `it == cend()` is guarded before the subtraction; nothing is drawn in that
  case anyway.

## Step 3 - rendering

`src/waveform/renderers/allshader/waveformrenderbeat.{h,cpp}`:

- The renderer now uses `RGBAMaterial` + `RGBAVertexUpdater` instead of
  `UniColorMaterial`, because one node needs two opacities. The RGBA shader
  writes `vec4(color.rgb * color.a, color.a)`, byte-for-byte the same
  premultiplied output as the unicolor shader, so ordinary beats are visually
  unchanged.
- Ordinary beats: same 1 px (logical) rectangle, same beat colour.
- Downbeats: `std::max(1, downbeatWidth)` logical px, centred on the snapped
  beat x (width 1 reproduces the old rectangle exactly).
- Downbeat alpha: `min(1, beatAlpha * 1.25 * downbeatColor.alpha)`; assumed
  patterns multiply that by `0.65`. With the default grid alpha of 90 % that
  is 1.0 for a detected downbeat and 0.65 for an assumed one, so an assumed bar
  line is visibly dimmer than a detected one.
- Stem tracks: both split-stem lanes and the non-stem path run the same loop
  and the same colour/width decision; the only branching that already existed
  is the rectangle shape (one per stem lane in split-slip mode, one full-height
  otherwise).
- Missing metadata: `downbeat::patternFor(invalid)` returns assumed 4/4 with
  phase 0. The data is not modified; only the rendering assumes a bar length.
  ADR-003 still holds: "unknown" stays unknown in storage.

`patternFor()`, `isDownbeat()` and the `Pattern` struct are header-only and
inline so the unit test can exercise the exact production logic without a
scene graph.

## Step 6 - grid-edit controls and bar sync

Not fixed here, as instructed. What the code does today:

- **Translate grid** (`tryTranslate`, quantized `tryTranslateBeats`): bars stay
  on the audio. The origin moves with the beats, so the ordinals that decide
  downbeats move with them.
- **Halve / double tempo** (`tryScale` with `BpmScale::Halve` / `Double`): the
  origin and `phase` stay fixed while the beat length halves/doubles. Bars keep
  starting on the same beat, but the bar duration in seconds becomes half or
  double the intended one. This is a genuine desync *if* the user used
  halve/double to correct an octave error (e.g. a 174 BPM track detected at
  87); until the grid is re-anchored or re-analyzed, the thick lines land on
  every other bar or two per bar. The renderer cannot detect this: `phase`
  has no notion of the absolute tempo factor.
- **BPM nudge / set BPM**: no desync; bar length follows the tempo, which is
  the intent.
- **Manual marker/beatmap edits**: preserved sub-version, ordinal semantics
  unchanged.

Recommended follow-up issue (not filed here, no GitHub access): when a
2:1 `BpmScale` edit runs on a grid with downbeat metadata, either clear
`DownbeatInfo` to "unknown" (so the UI falls back to the dimmed assumed bars
instead of confidently wrong ones) or halve/double the implied `phase`
appropriately. Clearing is the honest option and matches ADR-003.
