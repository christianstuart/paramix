## Flow as built

Open with the **Map** toolbar key (`res/qml/MainWindow.qml`, one button block
plus the `ControllerMapping` import; the Pad FX key is untouched). Opening shows
`ControllerMappingWindow.qml`:

1. **Device.** `syncDevices()` collects the MIDI entries of
   `ControllerManager.knownDevices` and `unknownDevices` into `midiDevices`.
   One device: selected and started automatically. Several: a device ComboBox,
   hidden when there is only one. The header shows the active mapping name and
   a bundled/user/new hint from `mapping.isUserMapping(Mixxx.Config)`.
   The window does not start learning until it is visible, so creating the
   window with the main window does not grab the controller.
2. **Move a control.** `ControllerLearning.start(device)` is called on show.
   The message card binds `ControllerLearning.lastMessage` and
   `existingMappingFor(lastMessage)`. It shows the hex triple, channel + 1, op
   code name, control and value, and either "Not mapped yet" or the control it
   is already mapped to (title from the picker inventory where available).
3. **Target.** The search list filters the picker inventory by title,
   description, category, group or key (180 ms debounce). Selecting a row calls
   `assign(group, key, options)`. The **Click a control** key raises the main
   window and installs `ControllerMappingLearnOverlay` over its content item;
   the first press resolves an item and calls the same `assign()`.
4. **Detected options.** `lastMessage.type` is displayed (Button, Knob
   (absolute), Relative encoder, 14-bit, Unknown). The **Override** ComboBox
   maps Auto / Button / Knob / Relative to a raw `options` mask for `assign()`:
   `Invert` (0x0001) and `SoftTakeover` (0x0400) are preserved from the guess,
   the type flags are replaced (Button 0x0020, SelectKnob 0x0200, absolute = no
   type flag). 14-bit is display-only, because the backend applies one mask to
   every suggested message; forcing it would mark both messages MSB.
5. **Session.** `pendingMappings` drives a ListView. **Undo last** is
   `removeAt(count - 1)`; **Delete** is `removeAt(index)`. A local `modified`
   flag, set from the `mappingChanged` signal and reset after start/save, also
   enables Save after a delete-only change.
6. **Save.** `save(mappingNameField.text)` returns the path; the path is shown
   and the state becomes "saved". Save closes the learning session in the
   backend, so **Continue** calls `start()` again for another session. Closing
   the window calls `stop()`.

Unsaved changes are lost on close, stated in the Save panel.

**Startup ordering.** `QmlApplication` loads `res/qml` before
`CoreServices::initialize()` registers the controller manager
(`src/qml/qmlapplication.cpp` line 163 vs 174). The mapping window is therefore
created eagerly with the toolbar but does not touch `Mixxx.ControllerManager`
until it is first shown: the `Connections` target is `null` while hidden and
`syncDevices()` runs from `onVisibleChanged`. `Mixxx.ControllerLearning` is safe
to create early because `QmlConfigProxy` is registered before the QML load.

## What learn-by-click actually does

`ControllerMappingLearnOverlay.qml` is declared in the mapping window but binds
its `parent` to `applicationWindow.contentItem`, so it becomes a full-surface
item in the **main** window. In learn mode the mapping window raises the main
window (otherwise its own top-level window would cover the target). On a press
the overlay hides itself, descends `childAt()` / `mapFromItem()` from the
content item to the deepest visible item, walks the parent chain, and accepts
the first item that:

- has string `group` and `key` properties,
- has a `[`-prefixed group,
- looks interactive (`pressed` boolean or `value` number), and
- matches an entry in the harvested control inventory (skipped while the
  inventory is still loading).

That resolves the control primitives that carry the pair: `ControlButton`,
`ControlFader`, `ControlKnob`, `ControlMiniKnob` (so transport, cue, faders, EQ
knobs, quick-effect knobs, crossfader, output knobs). It deliberately does
**not** use `rowForConfigKey()` from QML, avoiding a call through the
`QAbstractListModel*`-typed property.

It does **not** resolve items whose control only exists in a behaviour
(`HotcueButton`, `SyncButton`), a bare nested `Mixxx.ControlProxy` with no
item-level `group`/`key`, or non-inventory controls. In that case the overlay reports
"No mappable control under the cursor" and stays armed; the user uses the
search list. This is the honest P1 limitation from
`docs/controller-mapping-compatibility-plan.md` section 2.2.C: QML has no
generic way to read the `ControlProxy` behind an item, because `ControlProxy` is
a sibling object, not an item property.

**Smallest backend hook that would remove the limitation:** an explicit target
on the item, e.g. a C++ `QML_ATTACHED` `MappingTarget { group; key }` declared
next to the proxy in each control primitive, which the overlay reads first, with
the property/parent heuristic as a fallback. A second option is
`ControllerLearning.controlAt(Item*)`, returning the nearest `QmlControlProxy`
registered by the primitive. Either adds a C++ member to the QML layer, which PR
2 was not allowed to add, so it is reported here rather than written.

Cross-window reparenting is the one part that could not be exercised here. If Qt
refuses the reparent, the overlay would not catch the press; the search list
still maps everything. A follow-up should verify this on a desktop run.

## Registration mechanism

`res/qml/ControllerMapping` needs no `qmldir` and no CMake list entry:

- `Deck`, `Mixer`, `Effects` and `Library` are plain directories imported by
  path (`import "Mixer" as MixerComponents`). The new directory follows that
  pattern with `import "ControllerMapping" as ControllerMappingComponents`.
- `qmldir` files exist only for real QML modules (`res/qml/Theme`,
  `res/qml/Mixxx`); both were left untouched.
- A developer run loads `res/qml` from the source tree (the resource path
  resolves through `CMakeCache.txt`), so the new files are live on restart.
- Packaging already covers them: `install(DIRECTORY res/qml ...)` in
  `CMakeLists.txt` and the Android `copy_directory(res ...)` rule copy the whole
  tree.

## Top review risks

1. **Cross-window overlay.** The overlay moves itself from the mapping window
   into `applicationWindow.contentItem`. This is the only mechanism that gives
   learn-by-click without adding an item to `MainWindow.qml`, and it is
   unverified here. If it fails, only learn-by-click degrades.
2. **Control resolution heuristic.** Any item exposing `group`/`key` plus
   `pressed`/`value` is treated as a target and validated against the inventory.
   A composite item that forwards a valid pair could resolve to a control other
   than the one visually clicked. The session list makes a wrong assignment
   visible and deletable.
3. **Lifecycle and device identity.** The window stops learning on close, and
   re-starts on show. `syncDevices()` keeps the selected proxy alive across
   `deviceListChanged` by name/vendor/product/serial. If a device is recreated
   during a session, the backend may still hold the old `Controller*`; the UI
   only re-points `selectedDevice`.
