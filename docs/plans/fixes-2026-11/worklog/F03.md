# F03 worklog - audio pauses under high CPU load

## Summary

Issue #61 was seen once and has not been reproduced. This branch ships
diagnostics plus load-shedding for the background CPU consumers, and documents
what to capture next time. It does **not** claim a root cause.

## Diagnostics

### Counters on the audio callback

The audio callback cannot log, lock or allocate. Two lock-free values are
written there and read from the GUI thread:

- `CachingReader::cacheMissCount()` (`src/engine/cachingreader/`): a
  process-wide `std::atomic<quint64>` incremented with relaxed ordering on the
  existing cache-miss branch in `CachingReader::read()`. It counts chunks that
  a deck asked for while the reader had not decoded them. This is the
  starvation signal; a miss is filled with silence.
- `mixxx::audio::diagnostics::recordUnderflow(code)`
  (`src/soundio/audiodiagnostics.h`): a relaxed atomic store of the last code
  passed to `SoundManager::underflowHappened()`. `underflowHappened()` used to
  call `CmdlineArgs::Instance()` and `qWarning()` in developer mode; both are
  gone from the callback. The code is reported from the GUI thread instead.

### Report lines

`StemAnalysisCoordinator` already had a 500 ms GUI-thread timer. It now reads
`[App],audio_latency_overload_count` on every tick and emits at most one line
per second:

- `Audio dropout:` when the overload counter advanced.
- `Audio starvation (no device underflow):` when no underflow was counted but
  at least 4 cache misses arrived in that 500 ms tick. Reader starvation can
  feed silence through a healthy device callback, so this case would otherwise
  be invisible. The 4-miss threshold is a heuristic, not a silence
  measurement, and the line says so.

Both lines carry the same fields:

```text
underflow_code= <n>
[App],audio_latency_usage= <0..1>
cache_miss_delta= <misses since the previous line>
stems= active|idle
load_analysis= active|idle|suspended
batch_analysis= active|idle|suspended
stem_detail= active|idle|suspended
audio_latency_overload_count= <n>
```

The rate limiter keeps a cumulative cache-miss delta across the suppressed
window, so a burst is not under-counted. A counter reset by
`SoundManager::resetUnderflowCount()` (device setup) is adopted instead of
waiting for the count to climb back.

## Backoff state machine

One hysteresis machine in `StemAnalysisCoordinator` owns all background
pauses. It is evaluated every 500 ms on the GUI thread.

- **Band**: `0.60 <= usage <= 0.85`. Both consecutive counters reset. An
  existing pause is neither armed nor released.
- **High**: `usage > 0.85`. Increment `highTicks`, clear `lowTicks`. On the
  third consecutive high tick (1.5 s), if not already paused: set
  `m_pausedForOverload = true`, reset `highTicks`, and pause every owner.
- **Low**: `usage < 0.60`. Increment `lowTicks`, clear `highTicks`. On the
  second consecutive low tick (1.0 s), if paused: clear
  `m_pausedForOverload`, reset `lowTicks`, and resume every owner.
- Only those two transitions call the owners, so a pause is applied once and
  released once. The old "release the stem pause when no stem job runs" early
  return is gone: load analysis can be the reason for the overload, so the
  machine must run even with an idle stem queue.

Owners and what "not lost" means:

| Owner | Pause | Resume |
| --- | --- | --- |
| `StemService` | `setBackgroundPaused(true)`; worker waits at its next block | `setBackgroundPaused(false)`; user pause is still composed |
| `PlayerManager` | `setBackgroundAnalysisSuspended(true)`; scheduler workers suspend, queued tracks stay queued | `setBackgroundAnalysisSuspended(false)`; a track loaded during the pause does not clear it, because `slotAnalyzeTrack()` checks the flag |
| `StemDetailCache` | `setBackgroundSuspended(true)`; the debounce timer stops, `m_hasPending` and its key stay | resume restarts the debounce; the pending build starts once. A build already running is allowed to finish rather than being cancelled and lost |
| `AnalysisFeature` | receives `stemBusy || overloaded`, so the two owners compose | recomputed from both owners, never a blind `false` |

`StemDetailCache` is discovered lazily through
`WaveformWidgetFactory::isCreated()` because `CoreServices::initialize()`
constructs the coordinator before the QML application creates the waveform
factory.

## Mitigations

- Load analysis in `playermanager.cpp` now uses
  `max(1, min(8, idealThreadCount / 2))` workers, matching batch analysis, and
  passes `AnalyzerModeFlags::LowPriority`. (The scheduler also starts its
  threads at `QThread::LowPriority`; the flag makes the intent explicit and
  keeps the thread's own priority low.)
- `StemDetailCache`'s builder thread now starts at `QThread::LowPriority`. The
  renderer draws the previous picture until a build finishes, so this only
  delays the first stem waveform; nothing waits synchronously for a build.
- Post-separation re-analysis is deferred by 2 s in the `stemsReady` handler
  in `coreservices.cpp`, instead of deleting the old analysis and starting
  waveform/gain work while the separation worker hands the job back.

## Callback-path finding (not changed)

**Pre-existing violation:** the same cache-miss branch in
`CachingReader::read()` still executes

```cpp
Counter("CachingReader::read(): Failed to read chunk on cache miss")++;
```

`Counter` constructs a `QString` from the literal (heap allocation) and
`Stat::track()` builds a `StatReport` and looks the tag up in the stats
manager (a map lookup and queue write). This runs on the engine callback
exactly when the reader is missing chunks, i.e. the suspected dropout path.
Per the lane instruction this was reported rather than fixed; the new atomic
counter sits next to it. A follow-up should replace the `Counter` with the
atomic or remove it.

No lock was found in `CachingReader::read()` itself, and the PortAudio callback
was not traced exhaustively. Everything added to that path here is a relaxed
atomic.

## Scope review (files outside the plan's owned list)

The plan lists only `stemanalysiscoordinator.{h,cpp}` for the backoff, but the
coordinator cannot reach the load-analysis scheduler or the stem detail cache
from those files. The minimum wiring was:

- `src/mixer/playermanager.h` - declare `setBackgroundAnalysisSuspended()`,
  `isBackgroundAnalysisSuspended()` and `hasPendingLoadAnalysis()`. The `.cpp`
  part is the one-line thread cap plus the suspension plumbing.
- `src/waveform/stemdetail/stemdetailcache.h` - declare
  `setBackgroundSuspended()` and `isBuilding()`.
- `src/coreservices.cpp` - pass `m_pPlayerManager.get()` to the coordinator and
  defer the post-separation re-analysis.
- `src/soundio/audiodiagnostics.h` - new header-only atomic, so no
  `CMakeLists.txt` change. A static member on `SoundManager` would have forced
  the coordinator to include the heavy PortAudio header.

Each edit is small and limited to the feature. If the integrator prefers to
keep the owned-file list literal, the wiring and the stagger can be dropped
without reverting the diagnostics; the coordinator would then suspend stems and
batch analysis only.

## Verification

- No C++ toolchain, Qt, CMake, audio device or CI logs on this host. **Nothing
  was compiled, linked or run.**
- `clang-format 19.1.3` with the repository `.clang-format`:
  `--dry-run --Werror` passes on every changed `.cpp`/`.h`. Files that were
  already dirty were formatted whole, as the CI job checks whole files.
- `tools/paramix_audio_stress.py`: `py_compile` passes. `--print-recipe` runs.
  `parse_dropouts()`, `longest_report_gap_ms()` and the report path were
  exercised against synthetic log lines (both markers, midnight wrap, field
  parsing). The CPU-load path was not run end to end against a live app.
- The manual recipe was written from the code paths, not from a successful
  reproduction.

## Manual reproduction recipe

1. Build with stem separation and a real audio device.
2. Play lossless 44.1/48 kHz tracks on decks 1 and 2, crossfader and EQ neutral,
   no effects.
3. Keep two or three tracks queued for stem separation so the worker is busy.
4. Every 10 s load a different track into a stopped deck or sampler.
5. Use 128 frames (~2.9 ms) if supported, else 256 frames. Try the API that was
   in use when the pause was heard (Windows: WASAPI shared/exclusive, WDM-KS;
   Linux: ALSA, JACK; macOS: CoreAudio).
6. Run `python tools/paramix_audio_stress.py --cores <logical cores - 1>
   --duration 180` while audio plays.
7. Attach the `Audio dropout:` / `Audio starvation` lines plus the device API
   and buffer size to issue #61.

## What could not be verified

- Whether the pause is reader starvation, callback overrun, a device stall or
  GPU/render contention.
- Whether the 2 s re-analysis delay is enough on a slow machine; it is a fixed
  stagger, not adaptive.
- Whether the 4-miss-per-tick starvation threshold is quiet in normal use. It
  is capped at one line per second, but it may still fire on seeks.
- Whether lowering the stem detail thread priority is visible as a slower first
  stem waveform; it is bounded by the build itself.
- The exact reader-win condition: the existing `Counter` allocation may or may
  not be large enough to matter; it is reported, not measured.
